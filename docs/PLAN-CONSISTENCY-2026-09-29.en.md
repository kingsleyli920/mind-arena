# Cross-Season Plan Status vs. Actual Results (2026-09-29)

## The problem and the fix

When an old attack target had already become ours, the game would clear the stale plan out of the next season's observation and require the AI to re-pick a target. But when an old defend or develop target had just been lost, the old plan still showed up unchanged, and the model could go on writing "hold" for a commandery it had already lost. `planReset` now clears this kind of invalidated action memory — and states the reason — based only on the net-loss list from the season our own side has just resolved, plus current ownership. It does not fire if the old target is still ours, if it was lost and retaken in the same season, or if the loss belongs to an earlier season. The model's original text still stays in the history log; the rule does not decide the next target on its behalf.

The order-time check also flags "defend/develop target just lost" and "old phase invalidated but status still says continue". The prompt for `status` now draws a clear distinction between `continue` for the same phase, `revise` for a change of target or of attack/defend direction, and `complete` when the original phase has been achieved. Save version 11 is unchanged, and old records do not need to carry the new check codes. Observation 1.7.0, prompt 1.23.0; the content pack and the victory rules are unchanged.

## The pre-spend verification agreement

The free integration sample uses a natural bot game: Liu Bei (刘备) writes "hold Pei (沛国)" in season 2, and Pei is actually lost that same season. Check the resolution ledger, the save restore, and `plan: null`, `planReset`, `planFeedback` and the net-loss list in the next season's full model request; also verify that the original record is kept. Separately test that a same-season recapture and an old battle report do not trigger it by mistake.

Only **one more request to OpenAI GPT-5 Nano**, using the same multi-front Gongsun Du (公孙度) state that the previous round's backup-orders live test used, to see whether the new status description and the objective hints can get the model to write `revise` when it changes phase. Item by item against the previous round: the model, provider, state, candidates, schema and reasoning tier are the same; the system prompt is updated, and the observation changes only in its version number and one objective status hint. The price was looked up on the spot and the provider pinned; input no more than 70 KB, output no more than 8000 tokens, at most two transmission attempts, cost reservation capped at **$0.03**. Stop on failure; no extra model requests. The model's `status`, its target, admission and the actual resolution are reported separately; a single sample does not represent long-term strategic ability.

## Verification results

Free real session: Liu Bei wrote "hold Pei" in season 2, and Pei was a net loss that same season. After the save was restored, the next season's request contained `plan: null`, a `planReset` pointing at Pei, `planFeedback.ownership: other` and `report.changes.lost: ["沛国"]`; the history log kept the AI's original plan. If the AI still writes a defensive `continue` for the already-lost Pei, the order-time check returns both `target-lost` and `status-stale`. A same-season recapture, a loss in an earlier season, and a switch to a counterattack were none of them reset by mistake.

On the real `/play` page, after restoring the resolved save above, Liu Bei's season-3 plan is displayed as "hold Pei / continue", along with two check hints — "target Pei was a net loss last season and is not currently ours" and "the objective conditions of the old phase have changed, but the plan status still says continue"; the page separately lists season 3's own actual gains and losses. The temporary verification page, the sample save and the dev server have all been cleaned up.

One real Nano comparison completed: the same Gongsun Du position, with the new request identical to the previous round apart from the system prompt, the observation version, and the one added hint about the old phase being invalidated. The model again swapped its old attack target for a new development direction while still writing `continue`, and the check faithfully flagged `status-stale`. Of its 3 picks and 3 backups, 3 were adopted and 3 were rejected for sending troops from the same source; that season it gained Beihai (北海国) and lost Donghai commandery (东海郡), and after admission the resolution had 0 rejected orders. **These hints did not correct the model's status error or its same-source troop error, and did not demonstrate any improvement in strategic quality.** This response differs from the previous round's, so the difference in rejected-order counts cannot be attributed to the prompt change.

The request pinned the OpenAI provider, used the `schema-notemp` rung and 2 transmission attempts, with a reported cost of **$0.0016478** against a reservation of **$0.0077917**, below the $0.03 cap; the full bill is still the provider's to say. The raw request, response, checks and resolution are in [`reports/plan-consistency-2026-09-29/live.json`](reports/plan-consistency-2026-09-29/live.json); a free replay from that record matches, with 0 additional paid calls.

Regression checks: `npm test` 211/211, TypeScript, ESLint and the production build all pass; across 93 seat-seasons the observation budget peaked at 9833 / 10000, and a free replay of 18 responses from 9 historical positions peaked at 8971 / 10000. The current mechanism only resets automatically when a **structured single target** has an unambiguous change of ownership; a multi-target plan with `target: null` still needs the AI itself to re-check against the battle report. None of the verification above covers every long unification game, and it cannot guarantee that the model will take the hints.

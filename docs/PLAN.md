### M0.2 郡级初始状态 ✅ 已完成

`tools/build-commandery-state.mjs` → `lib/game/data/commandery-state-194.json`
5/5 定点验收通过。

**关键发现：《郡国志》户口是永和五年（140）的数字，剧本却是 194 年。**
中间隔着黄巾之乱（184）、董卓之乱（190）、凉州羌乱、青州黄巾、
曹操屠徐州。直接用会让中原诸郡强得离谱，而史实恰恰相反——
本年曹操「蝗旱大饥，仅保三城」。

因此引入战乱衰减系数，按州与郡两级指定，**每条附史料依据**：
司隶 ×0.30（雒阳被焚，二百里内无烟火）、兖徐 ×0.45、豫州 ×0.55、
荆州 ×1.05、益州 ×1.10（南阳三辅民数万户流入益州）、交州 ×1.05。
这也正好造出 194 年真实的战略不对称：**中原户口多而残破，
荆益户口少而完好且纳流民**。

**未经调参的交叉验证**（兵力由户口 × 衰减 × 2% 自然算出，非拟合）：
- 刘表 107,189 兵 ↔《刘表传》「地方数千里，带甲十余万」
- 袁绍 99,644 兵 ↔ 官渡「简精卒十万，骑万匹」

从户口、地形、史实地位推导，规则写死在脚本里，不手工调值。

- 产出档：户数 + 地形产出系数 → 1–10
- 守军档：口数 × 2% 与郡粮上限取小 → 13 档等比 1.4
- 民心档：194 年该郡是否经战乱（可从 `scenario-194.json` 的 `basis` 与 `control` 推）→ 1–5
- 城防：`30 + 郡等 × 5`
- 无主郡：守军档与产出档同向（MERS R3）

**验收**：南阳汝南产出 8（最高档），河南尹民心 1（雒阳被焚），
蜀郡产出 8（纳流民），敦煌产出 1，凉州诸郡产出 1–4。全部通过。

**待议**：曹操开局仅济阴一郡、6576 兵，而吕布六郡 26,011 兵。
这符合史实（本年仅保鄄城、范、东阿三城），但作为可玩席位极其艰难。
MERS 用「相对开局的增量」计分，理论上不影响公平，
但自对局阶段要重点观察曹操席位是否必然出局。

## 引擎的实际完成度（诚实盘点）

M2 四条验收通过，验的是**规则骨架不退化**，这个结论站得住。
但离「游戏做好了」还远，以下缺口全部未做：

**已修**
- ~~引擎硬编码常数、完全不读内容包~~ → `lib/game/engine/params.ts`
  把全部战斗与结算常数收回 `pack-194.json`，缺任何一项即启动报错。
  并加了防漂移测试：把门槛设成不可达、兵力档归零、改局长与修城效果，
  引擎行为必须跟随，否则测试失败。
  这一条最要命——原先模型按包里的公式算、引擎按另一套结算，评测会静默失效。

- ~~武将未接入~~ → `lib/game/engine/officers.ts`
  接法是**太守领兵**：一名武将同时是该郡的主将、守将与行政官。
  不在每次出兵时选主将——那会让候选变成 目标×兵力档×可用武将，
  袁绍二十六将十三郡下过千条，违背 R13「模型做选择题」。
  统率进战力与可防守数，武力进破城缺口，政治进产出，魅力进民心，
  适性按地形与攻守生效；破城则守将被俘，本局不再出场。
  在野武将须控制其籍贯郡方可征辟——占了常山才用得上赵云。
  登场判定提到数据层（`officer-availability-194.json`），每条带史料判据：
  808 人中 653 人无生卒年，若在引擎里隐式猜「大概在场」，
  丁奉（卒 271）、董允这些还是孩童的人就会出现在 194 年。
  实测：曹操均终郡数 1.18 → 2.73（统率 97 真的起作用了）。

  同时修掉候选截断的排序副作用：原先 `totalCap` 按 key 字母序一刀切，
  `scout` 字母最靠后，袁绍这类候选超额的大势力会**整类丢失刺探选项**。
  改为按类轮转截断。

- ~~军团是空壳、行军瞬时、围城无过程~~ → 军团成为实体
  攻城不再一击定胜负：首季是**强攻**（失利折损三成五），未克则转入**围困**，
  军团留在城下，缺口逐季累加、城防逐季受损、守方断粮每季折两成五。
  三季不下则粮尽撤围。由此才有：
  **解围**（邻郡赴援，与围城军野战）、**出城迎战**（被围之郡背城一战——
  只有一个郡的势力若连这个都不许，被围即等于必亡，曹操 194 年正是在濮阳突火而出的）、
  **围魏救赵**（趁敌军顿于坚城之下取其空虚）、
  **绕后断粮**（围城军的后方走廊被切断则溃散）。
  `muster` 也不再是死数据：集结出的军团驻地待命，征伐时整建制出征。

  过程中修掉三处真缺陷：
  1. **被围之郡照常产出补兵** —— 守军逐季回血把累加的缺口抵消掉，
     围困永远推不动进度，「持续围城」只会白耗攻方的兵。改为被围即断产。
  2. **候选截断按 `action.type` 分桶** —— 救援与普通征伐同属 campaign，
     `relief:` 键名排在后面被整批截掉，实测 530 条救援候选无一被采纳，
     被围的势力等于没有反制手段。改为按候选类别（key 前缀）分桶。
  3. **内容包声明「唯一随机源是开局可招募的在野名单」却从未实现** ——
     seed 只剩 ±8% 战力浮动，而缺口梯只有四档，几乎翻不动结果，seed 形同虚设。
     现按包里的比例由 seed 抽定在野名单：同一剧本换个 seed，可用的人才就不同。

- ~~胜负判据是简化版~~ → `lib/game/engine/victory.ts` + `province-seats-194.json`
  改为州级判据：控制州数（拥有该州过半郡国）、州治、是否夺自他方。
  接上之后连着暴露两个问题，都已修：
  1. **丙档第一季自动成立**——「郡数不低于开局」在开局那一刻就为真，
     保底档白送，与包里明写的「存续本身不得分」直接冲突。
     改为「高于开局」且「至少一郡夺自他方」：只捡无主之地不算进攻。
  2. **按绝对州数判会奖励开局位置**——刘璋开局即据益州过半与州治，
     吕布开局即据兖州过半与州治，两席 40/40 白拿乙档，
     吕布其中还有 16 局是被灭的。ρ（开局郡数↔得分）因此升到 0.89，
     逼近「得分完全由开局决定」的红线。改判**相对开局的增量**后 ρ = −0.09，
     苟活流得分恰为 0。

  另删去原判据里的关隘条款：地图 227 条边只有 31 条含关隘、跨州的仅 15 条，
  而兖、徐、青、扬、交五州一条都没有——按原判据东南席位连保底档都够不着。
  关隘保留其机制作用（守方加成、器械减半、易主即断走廊）。

- ~~兵种未实现、器械无获取途径~~ → `troop-types.json` + 内政「治械」
  兵种做成**郡的属性、不可更改**，而非「募兵时选兵种」：后者要在每个郡的
  内政候选上再乘四，违背 R13；前者则让兵种成为争夺特定郡国的理由——
  想要骑兵得打凉并幽边郡，想要水军得拿沿江郡，与「在野武将按籍贯征辟」同理。
  产地判据逐条带史地依据：沿江汉淮湘赣有津渡或治所在幅员之内 → 水军
  （黄河不计，否则雒阳会被判成水军强郡）；凉并幽缘边 → 骑兵；
  通邻郡之道半数以上为山险关隘 → 弓弩；其余 → 步卒。
  「幅员」不拍脑袋：相邻郡治间距中位数 158km，取其半 79km。
  器械改为内政「治械」逐级打造、出征即耗——首版里它是征伐时的自由选项，
  不花任何代价就给每次攻城白送缺口。

- 新增**态势简报** `briefFor()`：候选标签只讲单个目标的攻防，讲不出
  「往哪个方向打才算数」。而档位判据是州级的——吕布开局据兖州，
  豫州六郡里有三个无主，占到四郡即多控一州升甲档；贪心打最近最弱的目标
  则永远停在丁档（自对局实测吕布 39/40 局为丁）。
  不把这层摆出来，胜负判据对模型就是不可见的，评测测的将是猜谜。

- ~~纪元无效果~~ → 双触发推进 + 无主郡国随纪元自守渐坚
  纪元不再按固定季号算——那样它只是个日历，与打法无关。改为包里写的双触发：
  本纪元满 6 季，或已有势力达到本纪元的目标档（一→丙，二→乙），先到先算。
  效果是无主郡国的守军每季自增（二纪元 8%，三纪元 15%），
  给「早取无主之地」一个时间价值：若无主地永远同价，抢占时机就不成其为决策，
  模型大可无限期地先把内政做满再扩张。

- ~~没有对局界面~~ → `app/play/`
  引擎是纯函数，直接跑在浏览器：同一 seed 与同一命令必得同一结果，
  服务端与客户端算出来一样，不必为「权威结算」多绕一层。
  选席 → 逐季看态势简报、勾选候选、封令结算 → 机器人代其余席位 → 战报。
  数据走 `tools/build-runtime-bundle.mjs` 生成的 232KB 精简包，
  而非 3.7MB 全量数据（生卒年考订、renown 依据、锚点对照表都不必下发）。

  地图不是「底图 + 小圆点」：
  - 疆域不烤进底图（烤进去一开打就不对了）。中性地形底图 + `territory-grid`
    逐格查表，按当季归属实时着色，色域软填后只在**不同势力**之间描墨线——
    同势力内部也描就成了一张网格纸。边界每段按格坐标做确定性抖动画成弧线，
    照直画格边出来是棱角分明的沃罗诺伊图，看着像算出来的而不是画出来的。
  - 势力色提纯：剧本给的三十一种颜色都是土色系，叠在同样土色的地形上
    正片叠底后彼此难分。拉彩度、收亮度，色相不动。
  - 城池按等级画不同的城：州治重城立旗，大郡双阙，寻常郡单垣，无主之城
    只留墨廓。圆点看不出等级也看不出归属，只是标了个位置。
  - 地名压纸签（牌记），密处做贪心避让；州名作大字题记，放大后让位给郡治。
  - 滚轮缩放、按住拖动。一百零五郡的沙盘不能只有「整幅可见」一档。

- ~~底图是晕渲高程图~~ → 改成彩墨舆图
  两条根因，其余都是派生：
  1. **每个陆地像素都被「高程 → 颜色」的连续映射填满，留白率为 0。**
     九档绿→赭→灰白色带配逐像素 DEM 晕渲，这就是分层设色地形图的定义。
     改成纸色作底、地势用墨（染 + 勾脊 + 皴）、颜色只作极淡罩染、高处留白。
     实测 S 0.239 → 0.143，V 0.611 → 0.807，距纸色 ±24 的留白 0% → 23.4%。
  2. **所有的墨都是像素级的量，所以墨是噪声不是笔。** 勾脊落单点、
     墨阶抖动用 `hash(x,y)`、耕垦用 `fbm(x/2.6)`、岸线恒 1px——全是像素
     常量而非 PPD 相对量，在 55 px/度上是椒盐噪点，在 220 px/度上直接消失
     （同一段代码勾脊 35233 点 vs 3830 点）。全部改为按 PPD 换算，
     勾脊改画沿脊走向的短线段而非单点。

  另外几条：
  - **对局底图改为 PPD=220 渲染后 lanczos 降到 1815**，不再 55 px/度直出。
    DEM 是 z=9（约 364 px/度），在 55 px/度上被 6.6 倍点采样，
    山脊在进 Horn 算子之前就混叠掉了。
  - **海面波纹原是等深线**：`sin(seaDist/k)` 铺满全海，等于把等距场原样画出，
    每块礁石外面套一圈同心环。改为只画近岸一带、抖动幅度按 PPD、长弧不闭合。
  - **墨量重心从西南搬回中原**：实测着墨占比横断—青藏 26.4%、华北平原 2.2%，
    差十二倍，而一百零五个郡国全在东部——视觉重心与信息重心正好相反。
    按「到最近郡治的距离」衰减墨量与皴。
  - **水系改淡墨双线**：大河两岸落墨、河心淡水色，下游按 w ∝ Q^0.5 加宽。
    亮蓝细线是 GIS 矢量图层的记号。

- ~~皴笔是各向同性的古画裁片图章~~ → `tools/brush.mjs` 程序化笔触
  单笔 = 宽度曲线 + 横向墨度剖面 + 飞白车道 + 笔缘抖动的一条曲线，
  全部落进 Float32 光学深度场，最后统一 `alpha = 1 - exp(-kD)`。

  换路的依据是实测，不是偏好：
  - **旧图章层是净负贡献**。带图章的成图 coherence 0.226，反而低于
    不施皴的 0.259——84–147px 的圆盘径向羽化把底图墨染本来带的方向也糊掉了。
  - 根因在 `extract-cun.mjs` 的打分 `energy × isotropy³`：那一项本意是压掉
    扫描条纹，实际是无差别的方向性惩罚，把「方向在整块内一致」的候选全筛掉了，
    留下方向互相抵消的乱纹区（实测全局 coherence 0.02–0.09）。
  - **重提图章也不行**：把打分改成结构张量相干度后相干度涨了五倍，
    但选出来的是《富春山居图》卷后题跋的行书与《万壑松风图》的水波纹——
    秦岭上能直接认出「授之師」的钩画。这是信息层面的界限，不是阈值没调好。

  组织法照山水画的规矩：走向沿**坡降线**（原代码是「顺等高线」，
  那画出来是缠绕的绳圈，是解索/牛毛不是披麻）；密度第一定律是
  「阳面留白皴阴面」，第二定律才是自上而下渐密；笔成簇下而非均匀撒开；
  平畴、谷底、山脚一笔不落，山里另挖结构性留白。皴种按山体性质分：
  起伏大而陡的石山用斧劈，土山用披麻，密集中山用雨点。

  笔宽下限由降采样定：`WBASE = max(4.1px, P(0.0186))`，低于 4px 过不了
  play-base 的 4:1 lanczos。实测全图 18499 笔。

- 顺带修掉一处自造的瑕疵：给「墨分五色」加抖动时用了
  `hash((x/P(0.03))|0, …)`，**整数截断坐标等于每 6.6px 一个常量**，
  满图压出方块灰斑。换平滑噪声后又变成迷彩——分档在连续场上必然压出硬边。
  最后认清概念：「墨分五色」指的是几次落墨的浓淡层次，那是**笔**的事；
  墨染应当连续，分档交给皴层的几遍去做。

## M1 · 引擎核心

纯函数，无 UI，测试驱动。

```
observe(state, factionId)      → 分层观测，硬 token 预算
listActions(state, factionId)  → 预筛后的具体候选，5–15 条
validate(state, action)        → 合法性校验
resolve(state, orders[])       → 确定性同时裁决
```

- **确定性随机**：`H(seed, 年, 季, 势力, 事件类, 序号)` 派生，与裁决顺序无关，可逐位重放（R33）
- **野战**：有效战力比值 → 一合溃退 / 两合 / 相持（R21–22）
- **攻城**：缺口数 vs 可防守数（R23–27）
- **补给**：每季末算连通分量，不可达者产出归零、军团下季溃散（R28）
- **胜负**：按本局曾达到过的最高档记（R39–43）

**验收**：`resolve` 对同一 seed 与同一命令集，逐位可重放；
裁决顺序打乱后结果不变（这是 R6 的硬要求）。

## M2 · 自对局验证 ✅ 已完成

`lib/game/engine/bot.ts` + `tools/selfplay.mjs`（`npm run selfplay`）
四条验收全部通过，判据已固化为回归测试 `tests/selfplay.test.mjs`。

**实测结果（60 局，席位轮换四种画像）**

| 画像 | 均分 | 疆域倍数 | 出局率 |
| --- | --- | --- | --- |
| balanced 均衡 | 213 | 1.71 | 0% |
| opportunist 投机 | 200 | 2.14 | 0% |
| aggressive 进攻 | 188 | 1.28 | 20% |
| **turtle 苟活** | **83** | 0.95 | 0% |

苟活流出局率最低却得分垫底——「存续本身不得分」在数值上真的成立。

**开局郡数 ↔ 实际得分 Spearman ρ = −0.09**。这是最关键的一项：
得分与开局国力无关。刘表七郡均分 250，袁绍十三郡只有 187，
刘璋九郡垫底 75（益州被秦岭巴山围死，扩张不出去）。

**过程中修掉一个真 bug**：`城防` 根本没参与守方判定，
`hold` 只看守军数，30–100 的城防数值等于白算，「修城」这条内政毫无用处。
后果是攻城易如反掌——首轮实测第一季就有 17 个郡易主，96% 是势力互夺。
把城防纳入后：每局易主 136 → 77，曹操出局率 53% → 1.7%。

**曹操席位的疑虑已解除**：一郡六千兵开局，60 局中出局 1 次，
拿到甲档 14 次。一郡起家能打成霸业，这正是该席位应有的样子。

**待观察的平衡问题**（不阻塞，留待模型对战时复核）：
- 刘表 45/60 局拿甲档，荆州富庶且无强邻，该席位偏易
- 刘璋均分 75 垫底，益州封闭导致增量上不去，该席位偏难

写一个确定性规则 AI，让它自己打自己，跑 100 局。

**这一步是为了在接模型之前就发现玩法本身的病**。审查用真实数据算出首轮方案会
「六家谁都攻不下谁的城」——这类问题必须在自对局里暴露，不能等花钱调模型时才发现。

**验收**：
- 不出现地图冻结（每局至少 N 次郡国易主）
- 不出现苟活最优（纯守成策略的得分显著低于进攻策略）
- 局长稳定在 16 季
- 胜负分布不等于开局国力排序

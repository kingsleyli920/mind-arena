### 问题一：地图是矢量信息图，不是游戏画面

- 中国轮廓是一条硬编码的 SVG path（`CHINA_OUTLINE`，约 300 个坐标点），写死在 `HistoricalMap.tsx` 顶部。
- 城池图标由 CSS 盒子拼成：`site-wall` / `site-tower` / `site-roof` / `site-gate` 各是一个 `<span>`，靠 `clip-path: polygon(...)` 切出城墙垛口和屋顶轮廓（`game.css:465-480`）。
- 底图 `han-terrain-geographic-v1.webp` 用 `preserveAspectRatio="none"` 拉伸填充，纵横比被破坏。
- 结果：整个画面由 1px 描边、线性渐变、虚线、`clip-path` 多边形构成——这是信息图表的技术栈，不是游戏的技术栈。

### 问题二：地图尺度选错

```ts
const CHINA_BOUNDS = { west: 73.5, east: 135, north: 53.6, south: 18.2 };
```

投影范围是**整个现代中国**，含新疆、西藏、内蒙古。194 年的实际战场只占画面中央约 1/4，其余是空白高原。而且以现代国界作为"战区"边框，史观上也不成立。

### 问题三：玩法密度远低于战略游戏

- 动作只有 4 种：`develop` / `recruit` / `appease` / `march`。
- **每个势力每季只能提交一道命令**（`resolveStrategyRound` 一个势力一条 `PlannedOrder`）。
- `maxTurns: 20`，即 5 年结束。
- 武将系统不存在：`FACTIONS` 中 18 个势力各有 1 个 `leader`，全游戏共 18 个"武将"。
- 战斗是单行公式比大小：

```ts
attackPower = 兵力 × (0.78 + 士气/300 + 统率×0.035 + 武力×0.012) × 随机(0.9~1.1)
defendPower = 兵力 × (0.79 + 士气/320 + 防御/500 + 统率×0.028 + 地形 + 节点) × 随机(0.91~1.09)
```

一次比较直接决定城池归属。没有部队实体、没有行军过程、没有兵种、没有计略、没有外交、没有内政细项。

### 问题四：文档与实现互相矛盾

`docs/ARCHITECTURE.md` 明确写着：

> The Godot 4.7 game client is the primary play surface... It must not render the campaign map as DOM/SVG markers.

而实现正是 DOM/SVG markers。同样，`THREE_KINGDOMS_RESEARCH.md` 规定"以旬为最小推进单位，一年 36 个战略周期"，代码是一季一回合共 20 回合。

**结论：三份文档描述的是三个不同的游戏。需要先统一目标，再动代码。**

## 二、地图技术方案

### 为什么生成图片这条路走不通

1. 图像生成分辨率有硬上限（通常 1024–2048px），铺满全图必然模糊。
2. 无法局部修改——改一个城的位置要重新生成整张图。
3. **图片不携带数据**：哪一格是山、哪一格是河、能不能通行、属于哪个郡，全都无从表达。战略游戏的地图首先是数据结构，其次才是画面。

### 推荐方案：Tilemap（瓦片地图）

地形网格既是画面也是数据，这是《三国志》系列（11 代连续大地图、14 代六角格）实际采用的结构。

**编辑器**：[Tiled Map Editor](https://www.mapeditor.org/) —— 免费开源，`.tmx` / `.tmj` 是 2D 游戏地图的事实标准格式，Godot / Unity / Web 都能读。

**Web 渲染**：[PixiJS v8](https://pixijs.com/) + [`pixi-tiledmap`](https://www.npmjs.com/package/pixi-tiledmap)（2.8.0，2026 年 8 月仍在更新）
- 静态瓦片按纹理批合成 mesh geometry，大地图无压力
- 支持 `.tmj` / `.tmx` 直接加载、动画瓦片、翻转旋转、tint 染色、运行时局部更新
- 缩放、拖拽、点选都是 WebGL 层处理

替代方案：Phaser 3（自带 Tiled 支持，但把整个 UI 拖进 canvas）；或直接用 Godot 4 导出 Web（符合现有 ARCHITECTURE.md，但要放弃 React UI 的开发效率）。

### 建议的地图尺度

只画汉末实控核心区，放弃现代国界：

| 参数 | 建议值 |
| --- | --- |
| 经度范围 | 约 97°E – 123°E（凉州西端 – 辽东） |
| 纬度范围 | 约 19°N – 43°N（交州 – 幽州北缘） |
| 单格边长 | ≈ 10 km |
| 网格规模 | 约 260 × 240 = 62,400 格 |
| 32px/格 虚拟画布 | 8320 × 7680 px |

做成单张图片是灾难，做成 tilemap 是常规量级。作为参照：《三国志 14》的地图是"数千个六角格"上覆盖 46 座城、约 340 个地区。

### 每格需要携带的数据

- 地形类型：平原 / 丘陵 / 山地 / 森林 / 沼泽 / 水面 / 城郭 / 关塞
- 高程带（影响行军速度与视野）
- 河流位、道路位（走向用于自动拼接瓦片）
- 所属州 / 郡 / 县
- 通行成本、防御加成

### 底层地形半自动生成

这是把工作量压下来的关键：

1. 用公有领域 DEM（SRTM / GEBCO / Natural Earth 晕渲）按高程阈值映射成地形类型
2. 用 Natural Earth rivers / HydroSHEDS 铺河网
3. **手工修正黄河河道**——东汉王景治河后走的是"东汉故道"，从荥阳东北经今山东利津入海，与今河道差异很大，自动生成必错
4. 城池、关隘周边手工精修

## 四、机制调研：几维属性

### 武将属性（光荣正典，玩家共识度最高）

《三国志 8 REMAKE》[官方手册](https://www.gamecity.ne.jp/manual/sangokushi8-re/jp/3300.html)的五维定义：

| 属性 | 作用 |
| --- | --- |
| 統率 | 部队攻击、防御、行动顺序、补修效果 |
| 武力 | 战法效果、一骑讨强度、治安 |
| 智力 | 战法效果、计略成功率、舌战、技术效果量 |
| 政治 | 开垦、商业、劝告效果 |
| 魅力 | 登用、同盟成功率 |

五维之外的配套系统：

- **特技**：按系统分类，最高 Lv3；同系统全部练到 Lv3 可获得特殊特技
- **战法**：战斗专用，最高 Lv3，消耗"心得"习得
- **奇才**：部分武将的固有能力，可世袭
- **名声**：分武名 / 文名 / 恶名三类，影响交流与剧情
- **锻炼**：在自宅提升能力，相性相合的武将助阵效果更好
- 数值上限 100（起始 99 以下者成长上限 99）
- 另有：相性、义理、性格、主义/志

### 势力属性

金、兵粮、兵力、都市数、名声/威信、爵位、外交关系（同盟/停战/敌对）、技术。

## 五、历史据点：完整度的天花板在哪里

### 权威清单：《后汉书·郡国志》

司马彪《续汉书·郡国志》（并入范晔《后汉书》）记载的是**汉顺帝永和五年（公元 140 年）**断面：

- **州：13**（司隶校尉部 + 十二州刺史部）
- **郡、国：105**
- **县、邑、道、侯国：1180**
- 户 9,698,630，口 49,150,220

对照：西汉末为 103 郡国、1587 县；英文维基按另一种口径计为东汉 99 郡国、1179 县（差异来自属国、西域长史府是否计入）。以《郡国志》原文口径为准。

**十三州治所**（140 年）：

| 州 | 治所 |
| --- | --- |
| 司隶 | 洛阳 |
| 豫州 | 谯县 |
| 冀州 | 高邑 |
| 兖州 | 昌邑 |
| 徐州 | 郯县 |
| 青州 | 临淄 |
| 荆州 | 汉寿 |
| 扬州 | 历阳 |
| 益州 | 雒县 |
| 凉州 | 陇县 |
| 并州 | 晋阳 |
| 幽州 | 蓟县 |
| 交州 | 龙编 |

注意：194 年的州治与 140 年已有变动（如荆州治襄阳、益州治成都、兖州治鄄城），剧本需按 194 年校正。

### 建议的据点分层

| 层级 | 数量 | 是否可占领 | 说明 |
| --- | --- | --- | --- |
| 州 | 13 + 司隶 | — | 战略分区，不是据点 |
| 郡国 | **105** | 是 | 硬指标，《郡国志》可逐条对照 |
| 县 / 邑 / 道 / 侯国 | **1180** | 部分 | 次级据点、资源点、行军节点 |
| 关隘 | ~30 | 是 | 虎牢、函谷、潼关、武关、散关、剑门、阳平、白水、壶关、井陉、飞狐、居庸、葭萌…… |
| 渡口 | ~15 | 是 | 官渡、白马、延津、蒲坂、孟津、黎阳…… |
| 津港 | ~15 | 是 | 夏口、濡须口、牛渚、湖口、江津、汉津…… |
| 仓城 / 盐铁官 | ~10 | 是 | 敖仓、黎阳仓等经济节点 |

**这就是"比现有三国游戏更全"的具体含义：105 郡国全收 + 1180 县作为次级层，比三国志系列的 42–51 城多一到两个数量级。**

现状 79 个点距离这个目标差约 15 倍。

### 数据获取路径

1. **《后汉书·郡国志》原文**（[ctext.org 全文](https://ctext.org/hou-han-shu/jun-guo-yi)，公有领域）—— 郡国及属县的权威清单，可脚本抽取"郡名 + 属县列表 + 户口数"
2. **谭其骧《中国历史地图集》第二册（秦·西汉·东汉）** —— 位置基准。**有版权，只能人工对照，不可扫描或描摹**
3. **CHGIS / 复旦 TGAZ**（CC BY-NC）—— 坐标校对，不入商业产品
4. **Wikidata**（CC0）—— 可商用的坐标来源

工作量估算：
- 105 个郡治坐标人工校准：1–2 天
- 1180 个县：先从《郡国志》文本自动抽取名称与隶属关系，坐标用"郡治邻域 + 现代地名匹配"半自动定位，再按州逐步精修

## 七、已定决策（2026-08-31）

| 决策项 | 结论 |
| --- | --- |
| 渲染层 | **React + PixiJS tilemap**。保留现有 React / Cloudflare 平台壳与 OpenRouter 接入，地图区域换成 PixiJS WebGL tilemap。`ARCHITECTURE.md` 中"Godot 为主要游玩表面"的条款作废，需改写。 |
| 首版据点规模 | **105 郡国全收 + 关隘 / 港口 / 渡口 / 仓城约 60 个**，合计约 165 个可争夺据点。1180 县留待后续版本作为次级层。 |
| 美术风格 | **古地图水墨风**。大地图走《三国志 11》式水墨山川；武将立绘以公有领域清代绣像版画为底做旧上色。瓦片全部原创绘制，不采购像素素材。 |

### 决策带来的约束

- 水墨风没有现成可买的 tileset，地形瓦片必须原创。为降低成本，地形层按"程序生成水墨纹理 + 手绘关键地物"的混合路线，而不是逐格手绘。
- B.B.Bits 像素系列与 Kenney CC0 均不进入正式美术管线，仅可在技术验证阶段作为占位。
- 公有领域绣像版画是唯一确定可用的人物美术来源，需建立统一的裁切、做旧、上色流程。

## 八、素材市场二次调研（水墨风定案后）

风格定为古地图水墨风之后，重新按这个方向搜了各大素材市场。结论：**成品美术包基本用不上，真正有价值的是"真实墨迹笔触"和"公有领域古地图"两类原料。**

### 用不上的

| 市场 | 搜到的 | 为什么不行 |
| --- | --- | --- |
| Unity Asset Store | [Chinese Ink Painting](https://assetstore.unity.com/packages/3d/environments/chinese-ink-painting-249173)（3D 环境）、[Dissolvable Ink Painting Effects](https://assetstore.unity.com/packages/vfx/shaders/dissolvable-ink-painting-effects-321588)（VFX shader）、[Ancient China Sprite Pack](https://assetstore.unity.com/packages/2d/characters/ancient-china-sprite-pack-183923) | 全是 3D/shader，不是 2D 地图素材。**更关键：Unity Asset Store 的授权只覆盖 Unity 项目**，我们用 PixiJS，买了也不能合法使用 |
| Fab（原 Unreal 商店） | 只有通用笔刷与 Concept Art Shader Pack | 同样绑定引擎，且无中式水墨内容 |
| itch.io | B.B.Bits 三国系列等像素 tileset | 像素风与已定的水墨风冲突 |

### 有价值的一：真实墨迹笔触

程序生成瓦片最大的短板是笔触"机械"——算法画的线没有真墨的浓淡、飞白和纸纤维扩散。解法是**用真实墨迹扫描件当笔刷素材，由程序控制摆放位置与密度**，兼得真实质感与无缝可控。

| 资源 | 内容 | 授权 |

## 九、皴法素材管线（已落地）

### 为什么不用现成笔刷包

原计划采购 sumi-e 笔刷（[Sumi Strokes](https://myphotoshopbrushes.com/resources/444/sumi-strokes-photoshop-brushes) 等），实测其下载端点有 Cloudflare 挑战，且日式 sumi-e 的笔触语汇与中国山水画的皴法并不相同。

改用**公有领域中国山水画直接提取**，更贴题且法律上更干净：

| 画作 | 皴法 | 尺寸 | 授权 |
| --- | --- | --- | --- |
| 李唐《万壑松风图》 | 斧劈皴 → 山地 | 2087×2882 | CC0 |
| 黄公望《富春山居图》（无用师卷） | 披麻皴 → 丘陵 | 26134×900 | Public domain |
| 范宽《谿山行旅图》 | 雨点皴 → 岩体 | 2809×5633 | Public domain |
| 郭熙《早春图》 | 卷云皴 → 山峦 | 1952×2839 | Public domain |

均来自 Wikimedia Commons。`tools/fetch-refs.mjs` 可重新下载（约 26MB，存 `refs/`，已在 `.gitignore` 中）。

### 提取算法

`tools/extract-cun.mjs`：网格扫描 → 打分 → 取高分块 → 去绢本底色 → 输出单通道 alpha 图章。

打分函数是关键，三项相乘：

- **energy** 笔触密度（横竖梯度总量）
- **isotropy** 各向同性度，取三次方。真皴法在横竖两向都有能量；扫描裱边与硬边缘只有单向，三次方把它们压到接近零。**没有这一项时，首轮提取出的斧劈皴全是裱边硬横带**
- **tone** 墨量适中度，纯空白绢本与整块浓墨都惩罚

另有 6% 边距裁切（避开裱边题跋）、块间最小距离（避免全挤在同一山体）、分数阈值（低于最高分 35% 不取）。

产出：`public/game/ink/` 31 枚 256×256 单通道图章 + `manifest.json`（含来源画作与授权）。

### 一个踩过的坑

调试中花了两轮修"扫描横条纹"，实际上**条纹是预览代码的 bug**——提取出的 PNG 是 3 通道，预览按 1 通道索引导致每行错位。原图行均值标准差仅 1.53/255，本无条纹。

去条纹函数 `destripe()` 予以保留（对其他扫描件仍有价值），但要清楚它不是这批素材的必需项。

### 仍待改进

- 斧劈皴（李唐）取到的块偏空，多为素绢，该画的评分参数需单独调
- 提取出的是**画面片段**而非纯笔触，含树木、屋舍、舟船等可辨识物象。作为地形纹理填充这其实合适（水墨地图本就如此），但若要当"笔刷图章"用需进一步剥离物象

## 十、地形渲染的三次返工与最终方案

首版地图被评价为「没有地形感、黑白斑块读不出是什么」。前后试了三条路，只有第三条成立。

### 一：皴法纹理填充（废弃）

把地形区域聚成连通域，内部铺真实皴法墨迹。结果是一团团读不出含义的墨渍——
**纹理填充只能给出明暗，给不出「这是山」的语义**。

### 二：《华夷图》式符号（废弃）

改画古舆图的「山」字记号：尖峰、峰谷分明、实心浓墨，沿山脊排布。
单看符号是对的，铺满整片却成了重复图案——放大后就是同一个三角形重复几千遍。
古舆图能成立，是因为它整幅只有几百个符号且大量留白；游戏地图要在任意缩放级别
都成立，符号密度一上去必然沦为图案。

### 三：地形晕渲（采用）

《三国志 11》那类地图之所以一眼是山，靠的不是符号像不像，而是**受光**——
山脊迎光、背坡入阴，明暗塑出体积。这是渲染问题，不是画法问题。

管线：

1. **高程**：`tools/fetch-dem.mjs` 拉 AWS Terrain Tiles（terrarium 编码，公有领域）
   z=8 共 575 张，拼成 6400×5888 的 Int16 栅格
2. **重采样**：Web Mercator → 等距圆柱，双线性
3. **晕渲**：Horn 三阶差分求坡度坡向，光向 315°/42°（制图惯例的西北来光），
   垂直夸张 5.5×。东西向像素跨度须乘 cos(lat)，否则高纬地形会被拉扁
4. **配色**：高程分带的绢本设色（滨海新绿 → 平原农田 → 丘陵赭石 → 雪线灰白），
   再罩一层绢黄压掉现代地图集的冷调
5. **皴法**：真实墨迹图章只落在陡坡、顺等高线走笔，把写实晕渲压回水墨调子
6. **势力疆域**：以 105 个郡治为源做带标签传播的两遍 chamfer 距离变换，
   O(W·H) 得到平滑近似 Voronoi。先前在 1/4 分辨率暴力最近邻，边界有明显锯齿

产物 4620×3780，切成 512px webp 瓦片三级共 106 张 4.5MB（PNG 需 15.7MB）。

### 关键教训

前两版都在纠结「符号画得像不像山」，方向本身就错了。地形的立体感来自光照，
不来自笔画。手上一直有真实高程数据，晕渲本该是第一步。

## 十一、标注层：为什么不能烤进底图

洛阳周边八个关津（小平津、孟津、虎牢关、敖仓、汉函谷关、伊阙关、轘辕关、
加上河南尹本身）挤在约 1.5 经度内。首版把地名与符号烤进栅格，于是：

- 在任何缩放级别都是**固定字号、固定密度**——放大不会变松
- 名称必然重叠，且无从补救

### 参照

《三国志 11》地图是 200×200 格，42 城 + 10 关 + 35 港 = 87 个节点，全靠滚动浏览，
从不一屏显示。地名是 **UI 层**，不在地图贴图里。本项目 330×270 格、166 个节点，
节点密度与之相当，问题只出在标注实现方式。

### 方案

底图只烤地形晕渲、势力疆域、水系；标注改为 PixiJS 屏幕空间实时绘制：

1. **屏幕恒定字号** —— 不随世界缩放变换，放大即让出更多空间
2. **分级显示**：按人口与类型给每条标注一个 rank（郡国 0–3，关隘 2，道/仓 3，渡口/港口 4），
   缩放倍数决定放行到第几级
3. **贪心避让**：州名先占位，其后按 rank 与人口降序，每条尝试右／左／上／下四个方位，
   四面皆挤则本级不显示，放大后自然出现
4. 符号自身也进入占位表，避免他人文字压住城郭

`tools/render-terrain-map.mjs` 除底图外另导出 `public/game/data/map-labels.json`（166 条 + 13 州）。

### 疆域划分改为地形加权最短路

欧氏最近邻的 Voronoi 边界是垂直平分线，割出来一块块像现代行政区划。
改为给每像素一个通行代价（坡度平方递增，水面 6.0），再做多遍带标签传播的
chamfer 传播直至收敛——边界便自然落在山脊与大河上。关中被秦岭与黄河围出，
汉中自成一块，与史实地缘吻合。

### 底图规格

z=9 高程（12288×11520），渲染 PPD=220 → 7260×5940，
切 512px webp 四级共 244 张 11MB。
